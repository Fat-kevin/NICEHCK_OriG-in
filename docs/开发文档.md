## 1. 项目概述

### 1.1 背景

原道 OriG in「原点」是一款主打高性价比的旗舰级降噪 TWS 耳机，搭载恒玄 BES2700 系列蓝牙音频 SoC，支持 55dB 主动降噪、通透模式、入耳检测、LHDC V5 等特性。它的降噪/通透切换与左右耳独立电量等能力仅通过厂商配套的「原道 YUANDAO」手机 APP 暴露，**Windows 系统本身不提供任何控制入口**。

本工具的目标是在 Windows 桌面上补齐这一能力：连接耳机后，显示蓝牙名称、左右耳各自电量，并直接在电脑上切换「降噪 / 通透 / 关闭」模式。

### 1.2 目标

- 交付一个可直接运行的 Windows EXE（绿色版，免安装）；
- 连接/识别原道 Origin 耳机，显示设备名称；
- 显示**左右耳独立电量**（非合并单值）；
- 支持六态 ANC（关闭 / 通透 / 普通 / 深度 / 试验 / 风噪抑制）、七档中文 EQ、游戏、低延迟、双设备、入耳检测和抗风噪；
- 架构分层清晰、协议可插拔，方便未来适配其他品牌耳机；
- 代码规范统一，可测试、可维护、可扩展。

## 2. 技术调研结论

### 2.1 目标耳机硬件方案

调研结论（来源：IT之家、我爱音频网、耳机论坛等公开报道）：

- **主控 SoC**：恒玄 **BES2700 系列**蓝牙音频芯片，双模蓝牙（BR/EDR 音频 + BLE 控制）；
- **音频编解码**：LHDC V5，最高 24bit/192kHz；
- **降噪**：55dB 极限降噪深度，支持降噪 / 通透等模式切换（通过 APP）；
- **配套 APP**：「原道 YUANDAO」，负责音效切换、降噪控制、入耳检测设置等；
- **入耳检测 / 双设备连接**：均有硬件与固件支持。

**关键推论**：

1. 该耳机为**双模蓝牙**（BR/EDR 音频 + BLE）。原设计假设「控制能力必然通过 BLE GATT 私有服务暴露」，**2026-08-14 实测证伪**：GATT `fe2c123x` / `77777777` 全部写入无效果、无状态通知 → 非控制通道。正式控制实际走经典蓝牙 **RFCOMM/SPP `0000a100-1000-8000-4e48-434b4354524c`**，使用 NiceHCK/BES `4E | Len(LE) | 00 | Op(LE) | Payload` 协议；已验证固件、电量、ANC、EQ、游戏、低延迟查询响应。`df21fe2c` 的 `03` 头帧仅作辅助观察，不参与正式控制；
2. 恒玄 BES 方案在国产 TWS 中应用极广，其控制协议存在一定**方案级通用性**，但每个品牌（原道）会定制 UUID 与命令结构，**不能直接套用其他 BES 机型的协议**；
3. 私有协议目前**无公开文档**，需要按第 7 章的方法逆向获取。

> ⚠️ 这一条是整个项目的**最大不确定点**：若原道对 BLE 命令做了加密/签名（类似华为 FreeBuds 的加密握手），逆向成本会显著上升。落地前必须先完成「协议探测」（见 7 章）。

### 2.2 Windows 蓝牙访问技术选型

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| **WinRT `Windows.Devices.Bluetooth`（GATT）** | 微软官方 API，`DualApiPartitioned`，**桌面应用可用**；WPF 通过 `net8.0-windows10.0.19041.0` TFM 自动获得投影 | ✅ **采用** |
| Win32 Bluetooth GATT API（`BluetoothGATTGetServices` 等） | 底层 C API，无托管封装，需要大量 P/Invoke | ❌ 工作量大，弃用 |
| `InTheHand.Net.Bluetooth`（32feet.NET） | 第三方跨平台库，但对 WinRT/LE 支持与微软官方 API 相比弱 | ❌ 弃用 |
| `btleplug`（Rust）/ `bleak`（Python） | 其他语言栈，不适合本项目的 C# 选型 | ❌ 弃用 |

**项目配置要点**（WPF 正确引用 WinRT 的核心，避免 CS0234「Windows 命名空间不存在」）：

```xml
    <UseWPF>true</UseWPF>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <Platforms>x64</Platforms>

```

**Capability 说明**：

- 打包（MSIX）应用：需在 `Package.appxmanifest` 声明 `<DeviceCapability Name="bluetooth" />`；
- **非打包桌面应用**：绝大多数 GATT 客户端操作可直接工作；若个别 API 被 capability 拦截，兜底方案是改成 MSIX 打包发布，或嵌入外部应用清单。本项目**默认非打包绿色版**，遇到拦截再切打包方案。

### 2.3 电量获取方案

**结论：采用「标准通道 + 私有通道」双轨策略，私有通道优先。**

| 通道 | UUID | 数据 | 说明 |
| --- | --- | --- | --- |
| **标准 Battery Service** | Service `0x180F`，Characteristic `0x2A19` | 1 字节，0–100% | 单个合并值，多数 BES 耳机只在这里暴露「单耳电量」或「盒内总电量」 |
| **厂商私有通道**（目标） | 厂商自定义 128 位 UUID 特征 | 通常多字节：L/R 各自电量 + 盒电量 | **真正的左右耳独立电量在这里**，需逆向获取 |

**BES 方案常见规律**（用于逆向时辅助判断，不保证原道一致）：

- 私有电量特征通常可 **Notify**，随电量变化实时推送；
- 有的耳机只支持 Notify、不支持主动 Read（主动 Read 返回 `0x00` 的已知坑），因此**必须订阅 `ValueChanged` 事件**，不能只靠一次性读取；
- 读取字节需按特征 `PresentationFormats` 指数换算（通常无指数，但需校验）。

**读取策略伪代码**：

```
优先级 1：私有特征（左右耳独立）  → 解析 L/R 两个百分比，UI 分耳显示
优先级 2：标准 0x2A19            → 单值，UI 显示为「总电量」，左右耳同值
订阅 Notify：任何通道都订阅，电量变化实时刷新，不轮询
```

> **v0.2 实测补充（2026-08-14）**：双耳/盒电量**疑似走 SPP 而非 GATT**——`df21fe2c` 连接即推 `03 03 00 03 | 64 64 64`（3 字节 = 100/100/100，疑似 L/R/盒电量）。标准 `0x2A19` 通道仍可用作单值兜底（当前 UI 已用）。最终通道以逆向结果为准。

### 2.4 降噪/通透控制方案

**结论：无通用标准协议；本机型已确认走厂商私有 RFCOMM/SPP NiceHCK/BES 帧，不走 GATT 控制特征。**

社区已有多起同类逆向案例，证明了这条路径可行（但不保证原道协议未加密）：

| 案例 | 品牌 | 协议特征 | 参考价值 |
| --- | --- | --- | --- |
| `SonyHeadphonesClient`（开源） | 索尼 WH/WF 系列 | 0x2B 服务，`00002b01-…` 特征低位 nibble 即 ANC 等级；Windows 侧用 WinUSB 驱动绕限制 | 架构、协议解析思路 |
| `marshall-protocol`（开源） | Marshall Motif II | 私有 UUID 前缀 `-1337-1dea-feed-c0ffee70c0de`；命令走写特征 | 逆向方法论 |
| 华为 FreeBuds 逆向（博客） | 华为 | BLE 服务带**加密握手 + 会话密钥轮换** | ⚠️ 反面教材：若原道也加密，需评估成本 |

**模式枚举设计（领域层）**：

```csharp
public enum NoiseCancellingMode
{
    Unknown = 0,
    Off,           // 关闭（普通模式）
    AncOn,         // 降噪
    Transparency,  // 通透（环境声）
}
```

> 具体字节值（例如 `Off=0x00 / ANC=0x01 / Transparency=0x02`）在逆向后写入对应品牌适配器，领域层不感知。

> **v0.2 实测补充（2026-08-14）**：降噪/通透切换**走 SPP 命令驱动**——耳机状态变化不主动推（连接时仅推一次基线），APP 发命令、耳机回状态。SPP 帧格式初判 `03 <消息ID> 00 <载荷长度> <载荷…>`；命令字节待盲探 / JADX 原道 APP 提取。

## 3. 总体架构

### 3.1 设计原则

1. **依赖倒置**：高层策略不依赖底层细节，所有跨层依赖指向 Domain 中定义的接口；
2. **单向依赖**：Presentation → Application → Domain；Infrastructure/Protocol 实现 Domain 接口，向上依赖方向禁止回环；
3. **协议可插拔**：品牌相关的一切（UUID、字节解析、命令构造）隔离在 Protocol 适配器内，领域与界面零感知；
4. **硬件无关**：WinRT 调用只出现在 Infrastructure 的适配层，核心逻辑可脱离真机单元测试。

### 3.2 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│  Presentation 层（WPF 界面）                                  │
│  Views / ViewModels / 托盘 / 绑定 / 事件转发                  │
└───────────────────────────┬─────────────────────────────────┘
                            │ 调用用例
┌───────────────────────────▼─────────────────────────────────┐
│  Application 层（用例编排）                                   │
│  HeadsetConnectionService / BatteryMonitorService            │
│  NoiseCancellingService / 会话管理 / 重连调度                 │
└───────────────────────────┬─────────────────────────────────┘
                            │ 依赖领域接口
┌───────────────────────────▼─────────────────────────────────┐
│  Domain 层（领域模型 + 接口，纯 C#，无 UI / 无 WinRT）         │
│  HeadsetDevice / BatteryInfo / NoiseCancellingMode           │
│  IHeadsetConnection / IBatterySource / INoiseControlSource   │
└───────────────────────────▲─────────────────────────────────┘
                            │ 实现接口（依赖倒置）
┌───────────────────────────┴─────────────────────────────────┐
│  Infrastructure 层（蓝牙硬件访问 + 协议适配）                  │
│  ┌─────────────┐  ┌─────────────────────────────────────┐  │
│  │ WinRT 适配器 │  │  Protocol 适配器（可插拔）            │  │
│  │ DeviceWatcher│  │  StandardProtocol / BESProtocol     │  │
│  │ GattClient  │  │  YuandaoProtocol（逆向后填充）        │  │
│  └─────────────┘  └─────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

> **v0.2 补充**：Infrastructure 现有实现除 GATT 适配（`BluetoothDeviceScanner` / `GattDeviceSession` / `GattConnectionFactory`）外，已新增**经典蓝牙 RFCOMM/SPP 适配**（`RfcommServiceEnumerator` / `SppConnectionFactory` / `SppDeviceSession`），Domain 相应新增 `IRfcommServiceEnumerator` / `ISppConnectionFactory` / `ISppDeviceSession`。控制通道最终走 SPP（见 §7），GATT 仅保留标准电量兜底与探测用途。

### 3.3 依赖方向

- **允许**：上→下（Presentation→Application→Domain）；Infrastructure→Domain；
- **禁止**：Domain 引用任何上层或 WinRT；Application 不引用 WPF/WinRT 具体类型；
- 跨层对象一律使用 **DTO / 领域模型**，禁止把 WinRT 类型（`BluetoothLEDevice`、`GattCharacteristic`）传出 Infrastructure。

### 3.4 核心数据流

**电量数据流**：

```
SPP 连接推帧 / GATT Notify 事件
  → Infrastructure 适配器（解析字节为原始帧）
  → Protocol.YuandaoProtocol（解析出 BatteryInfo {L, R, Case}；SPP id=03 帧 3 字节）
  → Domain 领域模型
  → Application.BatteryMonitorService（缓存 + 变更事件）
  → Presentation ViewModel（PropertyChanged → 绑定刷新）
```

**降噪切换数据流（v0.2：走 SPP）**：

```
ViewModel 选择模式
  → Application.NoiseCancellingService.SwitchAsync(mode)
  → Protocol.YuandaoProtocol.BuildAncCommand(mode) → 字节帧
  → Infrastructure SppDeviceSession.WriteAsync(帧)   （SPP 流，非 GATT 特征写）
  → 耳机返回状态帧 → Protocol 解析确认 → ViewModel 更新 UI 状态
```

### 3.5 线程模型

- **UI 线程**：仅 WPF 绑定与事件转发；所有变更通过 `Dispatcher` 或 MVVM 工具库的 `MainThread` 调度；
- **蓝牙 IO**：WinRT 异步 → C# `async/await`，GATT 操作不阻塞 UI；
- **Notify 事件回调**：可能不在 UI 线程，由 Application 层聚合后以事件发布，ViewModel 负责线程封送；
- **规则**：`async` 方法全链路 `await`，禁止 `async void`（事件处理器除外，且必须 try/catch）；耗时 IO 不使用 `.Result/.Wait()`。

### 4.2 核心接口设计（Domain 层）

```csharp
// 设备协议：一个品牌一套实现，可插拔
public interface IDeviceProtocol
{
    Guid ServiceUuid { get; }                 // 私有控制服务 UUID

}
```


### 4.3 电量读取策略（Application 层实现）

`BatteryMonitorService` 聚合两条通道：

1. 连接建立后，枚举 GATT 服务表（`BluetoothCacheMode.Uncached` 防陈旧）；
2. 若发现私有服务 UUID（协议适配器匹配），注册私有电量特征 → 走 `YuandaoProtocol`；
3. 同时注册标准 `0x2A19` 作为兜底；
4. 每次收到 Notify 帧，按「私有优先」策略刷新 UI；
5. 订阅失败（特征不支持 Notify）则退化为定时读取（间隔 ≥ 30s，避免耗电）。

### 4.4 降噪协议适配器

`YuandaoProtocol : BESProtocolBase, IDeviceProtocol`

- 所有 UUID 常量与字节映射在逆向后填入，**逆向完成前适配器内抛 `ProtocolNotResolvedException`**；
- 命令重放安全：写特征时先 `WriteClientCharacteristicConfigurationDescriptorAsync` 使能通知，再写命令，最后等待确认帧（带超时）；
- 增加「回读确认」：写完后读一次当前模式，若与目标不符则抛出并提示，避免 UI 假成功。

### 4.5 状态机与重连

连接会话状态机（`HeadsetConnectionService`）：

```
Disconnected ──连接──▶ Connecting ──成功──▶ Connected
     ▲                      │失败            │
     └──── 重连(退避) ───────┴──────── Notify 断开 ──▶ Reconnecting
```

- 断开自动重连：指数退避（1s → 2s → 4s，上限 30s）；
- 重连成功后自动恢复电量订阅，并回读当前降噪模式同步 UI；
- 全部状态变化以事件发布，ViewModel 订阅刷新。

### 4.6 配置与持久化

- `appsettings.json`：日志级别、重连参数、协议开关；
- 用户配置（记住上次连接设备、默认降噪模式）：`%LocalAppData%\YuandaoTws\config.json`；
- 无数据库，避免引入额外依赖。

## 5. 代码规范

### 5.1 通用规范

- 代码、注释、提交信息统一使用中文；标识符使用英文；
- 每个文件 ≤ 400 行（超限拆分）；每个方法 ≤ 40 行（超限拆分）；
- 禁止使用 `#region` 大块包裹（用拆分文件替代）；禁止魔法数字（定义为常量/枚举）；
- 提交信息格式：`<type>: <subject>`，type ∈ `feat/fix/refactor/docs/test/chore`。

### 5.2 C# 命名规范

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 命名空间 | `PascalCase`，按项目层级 | `YuandaoTws.Application.Services` |
| 类 / 接口 | `PascalCase`；接口前缀 `I` | `BatteryMonitorService`、`IDeviceProtocol` |
| 方法 | `PascalCase`（动词短语） | `GetBatteryAsync`、`SwitchModeAsync` |
| 属性 | `PascalCase` | `LeftEarPercent` |
| 常量 | `PascalCase` | `BatteryServiceUuid` |
| 私有字段 | `_camelCase` | `_gattClient` |
| 局部变量 / 参数 | `camelCase` | `deviceInfo` |
| 异步方法 | 后缀 `Async` | `ReadOnceAsync` |
| 事件 | `PascalCase`，`ValueChanged` 式命名 | `BatteryChanged` |

### 5.3 分层职责边界（红线）

| 层 | 允许 | 禁止 |
| --- | --- | --- |
| Presentation | 绑定、ViewModel 状态、命令触发、UI 调度 | 直接调用 WinRT；解析蓝牙帧；写业务规则 |
| Application | 用例编排、会话/缓存/重连策略 | 引用 WPF/WinRT 具体类型；写解析逻辑 |
| Domain | 领域模型、枚举、接口、纯算法 | 引用任何 UI/WinRT/基础设施类型 |
| Infrastructure | WinRT 封装、字节 IO、协议解析 | 反向依赖上层；包含业务用例 |

> 判定方法：任意层文件的 `using` 语句不得出现其下方各层命名空间（WinRT 的 `using Windows.*` 只允许出现在 Infrastructure）。

### 5.4 异步规范

- `async/await` 全链路，禁止 `.Result` / `.Wait()`（会产生死锁或 UI 卡顿）；
- 库代码使用 `ConfigureAwait(false)`；事件处理器中允许 `async void` 但必须 `try/catch` 包裹；
- 可取消操作一律接受 `CancellationToken`；
- GATT 读写都要设超时（`CancellationTokenSource.CancelAfter`），防止永久挂起。

### 5.5 错误处理与日志

- 自定义异常体系：`DomainException`、`BluetoothConnectionException`、`ProtocolException`、`ProtocolNotResolvedException`；
- 分层捕获：Infrastructure 抛领域化异常（包装 WinRT 异常），Application 记录日志并转换为领域错误，Presentation 转 UI 提示；
- **禁止空 catch 吞异常**；异常必须包含上下文（设备、UUID、操作、帧 hex）；
- 日志级别：Debug（帧级）/ Info（状态变化）/ Warn（重连、降级）/ Error（异常）；
- 电量帧解析失败要记录完整 hex 帧，便于逆向阶段校准。

### 5.6 单元测试规范

- 测试框架：xUnit + `NSubstitute`（Mock）+ `FluentAssertions`；
- **协议解析逻辑必须 100% 覆盖**（`BatteryInfoParserTests`、`AncCommandBuilderTests`），用从真机抓包得到的帧做测试用例数据；
- 领域层测试不依赖任何硬件/模拟器；Infrastructure 层用接口隔离后测试字节流处理；
- 覆盖率目标：Domain ≥ 80%，Application ≥ 60%，Presentation 手动验证。

### 5.7 代码评审清单

- [ ] 依赖方向是否符合分层红线？
- [ ] WinRT 类型是否泄漏出 Infrastructure？
- [ ] 是否存在 `async void` 未捕获、`.Result`、空 catch？
- [ ] 协议解析是否覆盖异常帧（长度不足、超界值）？

## 7. 协议逆向方案（关键前置任务）

> 第 2 章结论：降噪/通透切换与双耳电量的私有协议**必须先逆向**。已确认控制通道为经典蓝牙 SPP（见 §7.0）。本阶段交付「SPP 命令逆向」与「协议文档」，通过后才能进入功能开发。预计 3–5 个工作日。

### 7.0 实测结论（v0.2，2026-08-14）：控制通道 = 经典蓝牙 SPP

**GATT 方向已判否**：`probe\session-20260814-093906.txt` 判定性负实验（触控切 ANC 期间 `fe2c123a` 读值恒定）+ 全部 GATT 写入无效果、无状态通知 → `fe2c123x` / `77777777` 不是原道 APP 的控制通道。

**SPP 方向已确认**：`df21fe2c-2515-4fdb-8886-f12c4d67927c` 打开流成功，连接即推 3 帧基线状态：

| 帧头 | 载荷 | 含义（初判） |
| --- | --- | --- |
| `03 01 00 03` | `44 18 D8` | 未知 |
| `03 02 00 06` | `6C A9 CC 75 1E A4` | 设备标识 |
| `03 03 00 03` | `64 64 64` | **100/100/100，疑似 L/R/盒电量** |

帧格式初判：`03 <消息ID> 00 <载荷长度> <载荷…>`。状态变化不主动推（70s 观察无推帧）→ **命令驱动**。完整记录见 `docs/protocol/yuandao-origin.md` §3.10–3.13。

### 7.1 目标

1. 定位 SPP 控制服务并确认（`df21fe2c` 已确认；`66666666` / `99999999` 待排）；
2. 提取 / 盲探**命令字节**（降噪三态切换、电量查询/通知）；
3. 得出命令帧与状态帧格式，形成 `docs/protocol/yuandao-origin.md` 协议文档；
4. 填入 `YuandaoProtocol`（接入点见 `docs/交接文档.md` §7），解锁 M2 双耳电量与 M3 降噪切换。

### 7.2 工具链

| 工具 | 用途 |
| --- | --- |
| 本项目「SPP 探测」窗口（✅ 已实现） | 枚举已配对经典设备 → SDP 服务 → 开流收发 → 会话记录 `probe\spp-session-*.txt` |
| JADX | **首选**：反编译原道 APK，提取 SPP 服务 UUID 与 `BluetoothSocket` / `OutputStream.write()` 命令构造代码 |

### 7.3 操作步骤

**A. 服务定位（已基本完成）**：SPP 窗口枚举已配对设备 SDP → `df21fe2c` 确认可开流并推基线帧；继续验证 `66666666` / `99999999` 是否为真正控制服务（两者为 BES 白牌魔数 UUID）。

**B. 命令格式盲探**：df21fe2c 开流后发 `03 <cmd> 00 00` 系列查询（`03 01 00 00` / `03 03 00 00` / `03 04 00 00`…），看是否重推/回状态 → 确认命令帧格式 `03 <cmd> 00 <len> <payload>`。

**C. 反编译 APK（JADX，拿到命令字节的确定路径）**：

- 导出原道 APP APK → 定位 `BluetoothSocket` / `connect()` / `OutputStream.write()` 调用；
- 搜索 SPP 服务 UUID（验证 `df21fe2c`）与命令构造代码；
- 观察命令是否带加密/签名（base64、时间戳、session——**判断是否可重放的关键**）。

**D. 真机帧对照（可选）**：Android 开 HCI snoop + 原道 APP 切降噪/看电量 → `adb pull btsnoop_hci.log` → Wireshark 用 `btrfcomm` 过滤 RFCOMM 数据帧，对照 Windows 端 SPP 探测结果。

**E. 协议落地**：命令字节与解析逻辑填进 `YuandaoProtocol`，补单测（用真机帧做用例数据）。

- `YuandaoProtocol` 适配器实现（SPP 收发 + 帧解析）；
- 测试用例帧数据（L/R 电量、三态降噪各一帧）。

### 7.5 决策点

| 探测结果 | 后续决策 |
| --- | --- |
| 命令明文可重放 | ✅ 正常开发，适配器按协议实现 |
| 命令带简单校验（CRC/校验和） | ✅ 适配器补校验算法即可 |
| 命令带加密/签名/会话密钥 | ⚠️ 评估成本，可能只能实现电量；或与用户确认是否接受 |
