## 3. 关键发现（重要）

1. **未配对设备的特征写入被 Windows 拒绝**（`UnauthorizedAccessException` / `COMException 0x80650003`）。
   - 读取与订阅未配对设备**可用**，但**写入必须配对**。
   - 用户在 Windows 删除设备后处于未配对状态 → 之前所有写试探全部失败，耳机无反应。
   - **对策：应用内已加「配对」按钮**（`GattConnectionFactory.PairAsync`，Just Works `ConfirmOnly`），配对成功后才能写入。
2. 已订阅的 `fe2c1234/1235/1237/123a`、`77777777`、`a100-1002` 均**无主动通知**——耳机不会主动推状态，需**写入命令触发**。
3. 连接不稳定：会话频繁 Closed → 自动重连，部分时段 `Unreachable`。重连期间 GATT 操作会失败。

## 3.5 全自动试探结果（2026-08-14）—— 协议**疑似加密**

对 5 个候选控制特征写入 20 个候选命令（`01/02/03…`、`FE 01…`、`AA 01…`）后：

| 特征 | 结果 |
| --- | --- |
| `fe2c1234` | 全部写入无通知、状态寄存器不变——无反应 |
| `fe2c1235` | **每个写入都回推 16 字节随机数据**（每次不同，如 `CE 06 FD 2C 5B 5D E4 BC…`）→ **疑似加密/会话协商通道** |
| `fe2c1237` | **全部写入失败**（可能要求特定格式/长度或 WriteWithoutResponse） |
| `fe2c1236` | 写入成功但无通知、状态寄存器不变 |
| `77777777` | 写入成功但无通知、状态寄存器不变 |

**结论**：`fe2c1235` 对任意输入回推 16 字节随机数据、`fe2c123a` 读值每次变化——是典型的**加密握手/会话密钥协商特征**。盲写命令无法生效，需先完成加密协商。这与 `docs/开发文档.md` §7.5「命令带加密/签名」决策点吻合：**若加密，只能实现标准电量或放弃降噪切换，除非破解协商**。

**响应帧字节级分析**（21 帧 × 16 字节，2026-08-14）：无校验和（末字节 ≠ 前 15 字节 XOR/SUM）、输入-输出无线性关系（同差值输入的输出 XOR 完全不同）、字节熵 7.4 bit/字节（接近纯随机）。⚠️ 但每个输入值只写了一次，**尚不能区分「固定密钥确定性加密」与「随机 nonce/会话密钥」**——同一值重复写入，响应相同则前者（可继续分析），不同则后者（真加密）。此判据由 probe v2 的「确定性测试」给出。

**观察实验结论（2026-08-14）**：用户戴耳机触控长按来回切换降噪/通透/关闭（确认已操作），30s 内 `fe2c1239` 恒为 `01 00 81` 且收到 0 通知 → **降噪状态不通过只读 GATT 暴露**，`fe2c1239` 与降噪无关（见 §2）。耳机只会在收到写入命令后回推数据，不会主动推状态。

**fe2c1237 写入全失败**（2026-08-14）：21 次带响应写全部 ~85ms 内快速失败，异常消息为空。枚举属性把 Write 与 WriteWithoutResponse 合并显示为「写」→ 疑似**仅支持无响应写**。probe v2 已改为对 fe2c1237 使用 WriteWithoutResponse 重试。

**待验证**（probe v2，2026-08-14 构建）：①fe2c1235 确定性测试（同值×3）→ 固定密钥 vs 随机 nonce；②fe2c123a 写试探（回写读值/全 0/全 FF）+ 握手前后 fe2c1235 响应对比 → 能否建立会话；③fe2c1237 无响应写；④16 字节整帧候选值。

## 3.6 probe v2 结果（2026-08-14 上午）—— 会话协议是活的，但非简单 AES

1. **fe2c1237 确认仅支持无响应写**：切换 WriteWithoutResponse 后 26 次写入全部成功（此前带响应写全部失败），但无任何通知。
2. **fe2c1235 响应是「当前状态的确定函数」而非随机数**：确定性测试中 `01`×3 与 `03`×3 响应**完全相同**（16 字节逐字节一致）；仅 `02` 首次响应异常（`7E 5A D0…` → 之后稳定为 `D5 07 A0…`）→ **`02` 疑似特殊命令（触发状态转移）**。
3. **fe2c123a 是会话状态通道**：每次写入 fe2c123a 均收到 16 字节通知、读值变化，且**此后 fe2c1235 对同一输入 `01` 的响应随之改变**（7 次不同响应 × 7 个状态）。
4. **同一状态值 `k0 = 26 31 27 81…`（fe2c123a 读值）下，`01` 的响应三次不同**（主试探 `8F 26 D0…` / 确定性 `BE AD CF…` / 会话基线 `A4 14 88…`）→ 响应不是 (输入, fe2c123a读值) 的纯函数；**16 字节整帧写入 fe2c1235 或写其它特征也会改变会话状态**。
5. **AES 假设全部落空**（.NET Aes 实测）：E(fe2c123a读值, 01补齐) ≠ 响应；fe2c123a 状态转移关系（E(old,写值)=通知/新读值、密钥封装等 24 种组合）全部不匹配 → **非「读值即密钥 + AES-ECB/CBC」的朴素结构**，需更多同状态映射数据或握手线索。
6. 附带：`fe2c123a` 读值在**跨天会话开始时相同**（08-13 与 08-14 均为 `26 31 27 81…`）→ 非每次连接随机，可能源自配对/序列号。

**下一步（probe v3）**：同状态映射表（各值×3 建立输入→响应表、`02` 放最后隔离其副作用）→ fe2c123a 写矩阵（各负载×重复，观察通知/读值/fe2c1235 响应联动）→ 跨特征写入是否改状态的探针（分别写 fe2c1237/7777/1234/1236 的 16 字节帧后重试 `01` 响应）；**两次连接各跑一遍对照**，判定会话状态是否跨连接稳定。

## 3.7 probe v3 结果（2026-08-14 上午第二轮）—— 状态位 + 跨会话重现

**两轮运行（断开重连后各跑一遍）+ 两次观察，交叉比对 60+ 组 (输入→响应)：**

1. **`fe2c1239` 字节 0 是「可写控制、跨重连保持」的状态位**：v3 第一轮运行中从 `01 00 81` 变为 `02 00 81`（此前的 v1/v2 全部探针期间恒为 `01`），第二轮连接开始即 `02 00 81` 并保持 → **某个写入翻转了它，且该状态持久**。已定位的候选翻转写入待 v4 逐步跟踪确认。
2. **响应存在「跨会话完全重现」**（不同连接、不同 fe2c123a 读值，响应逐字节一致）：
   - `01 00` → `EC CC E0 D5 A1 84 9D 62 DE B1 7E 52 F4 30 3E 58`（v2 与 v3r2，且两轮 1239 状态不同）
   - `02 01` → `C5 1C E7 B7 68 96 4F 4D BB F3 E5 6B E8 6C 43 D1`（v2 与 v3r2）
   - `01 02…10`(16B) → `20 0A C6 C7 19 85 BA 07 DC 18 7C 15 61 7A 45 EA`（v3r1 与 v3r2）
   - `04` → `C4 FD 16 55…`（v2 与 v3r1，两轮均为 1239=01 态；v3r2 的 02 态下不同）→ **04 的响应随 1239 状态位变化**
   - `02` 连写收敛值 `D5 07 A0 45…`（v2 第 2/3 次 = v3r1 第 3 次；v3r2 未收敛）
3. **不重现的输入**：`01`（三次会话三个值）、`03`、`05`、`FE 01` → 依赖会话/隐藏状态。
4. **`fe2c123a` 是滚动值而非连接级固定密钥**：写矩阵后变化、跨特征写后也变、两次连接的初值互不相同。
5. **判定**：不是「每次连接随机密钥」的真加密，而是**小型状态机 + 固定函数**的组合——部分输入（0100/0201/16B 等）响应与连接无关（固定函数/查表），部分输入（01/02/03/05）响应随状态位（fe2c1239 字节 0 可见轴）+ 隐藏轴变化。**可继续逆向，前景乐观。**

**下一步（probe v4，已构建）**：逐步状态跟踪——对每次写入记录 fe2c1239/fe2c123a 前后值，定位翻转 `01↔02` 的具体写入；再以状态位为轴建立两态映射表，重建状态机。

## 3.10 GATT 控制通道证伪 → 转向经典蓝牙 RFCOMM/SPP（2026-08-14）

1. **判定性负实验**（`probe\session-20260814-093906.txt`）：触控切通透→降噪期间，`fe2c123a` 读值恒为 `26 31 27 81 89 CA E7 A8 CF 89 1F 3A 02 F6 FA 67` → **证伪** §3.8.3「fe2c123a 初值 = f(ANC 模式)」，且该值不跟踪 ANC 状态。
2. 综合 §3.5–3.8 全部「写入无可见效果、无通知、状态寄存器不动」，判定 **GATT fe2c123x / 77777777 不是原道 APP 的控制通道**（更可能是 BES 固件自带接口 / 诱饵）。
3. 用户结论（来源待确认）：耳机控制走**经典蓝牙 RFCOMM/SPP**，非 BLE GATT。与「fe2c123a 读值跨天恒定」吻合——GATT 端本就没有真实控制状态。
4. **应用已加「SPP 探测」窗口**（`SppProbeWindow` + `SppProbeViewModel`）：枚举已配对经典蓝牙设备的 SDP RFCOMM 服务（找 SerialPort 0x1101 / 厂商自定义 UUID）→ `StreamSocket.ConnectAsync(ConnectionHostName, ConnectionServiceName)` 打开 SPP 流 → 发送/接收 hex + 会话记录（`probe\spp-session-*.txt`）。分层：Domain 新增 `IRfcommServiceEnumerator` / `ISppConnectionFactory` / `ISppDeviceSession` + `RfcommServiceNames`；Infrastructure 实现（`RfcommServiceEnumerator` / `SppConnectionFactory` / `SppDeviceSession`）；Application `SppProbeService`。
5. **后续逆向方向**：① 先用 SPP 窗口枚举确认通道存在；② 命令字节优先从原道 APP（JADX）提取（`BluetoothSocket` 的 SPP 服务 UUID + `OutputStream.write()` 命令帧），Android HCI snoop 作真实帧对照；③ Windows 盲探兜底。
