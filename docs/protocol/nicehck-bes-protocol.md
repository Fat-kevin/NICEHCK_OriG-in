## 2. 完整协议解码（NiceHCK 实测协议）

### 2.1 帧格式（6 字节头 + 载荷）

```
4E | <Len_LSB> <Len_MSB> | 00 | <Op_LSB> <Op_MSB> | <Params...>
```

| 字节 | 字段 | 说明 |
| --- | --- | --- |
| 0 | Magic | 固定 `0x4E`（'N'） |
| 1-2 | Len | **载荷长度**，小端 2 字节；`Len = 3 + Params 长度`（3 为 Op 2 字节 + 保留 1 字节） |
| 3 | Reserved | 固定 `0x00` |
| 4-5 | OpCode | 小端 2 字节功能码 |
| 6+ | Params | 参数（查询命令无参数，Len=3） |

- **总包长 = Len + 3**（Magic 1 + Len 2）
- 帧解析（`protocol.rs` PacketStreamParser）：找 Magic → 读 Len（小端）→ 校验 Len ∈ [3, 4096] → 包长 = Len+3 → 读 Op → 读 Payload（= 包体第 6 字节起）
- 支持粘包/拆包/脏数据重同步（先丢弃 Magic 前数据，长度非法则逐字节重扫）

### 2.2 OpCode 表（Android `NiceHckProtocol.Op` 与 Rust `protocol.rs` 完全一致）

| OpCode | 方向 | 含义 | 命令帧（hex） | 响应帧 |
| --- | --- | --- | --- | --- |
| `0x0003` | 查询 | 固件版本 | `4E 03 00 00 03 00` | `4E 04 00 00 03 00 <sub> <main>`（payload=[sub, main]，如 `08 04` = 4.8） |
| `0x0005` | 查询 | 电量 | `4E 03 00 00 05 00` | `4E 06 00 00 05 00 <L> <R> <Case>`（payload=[L,R,Case]，**Case=0 表示未知/保持上次**） |
| `0x0101` | 查询 | 降噪模式 | `4E 03 00 00 01 01` | `4E 04 00 00 01 01 <mode>` |
| `0x0201` | 设置 | 降噪模式 | `4E 05 00 00 01 02 <mode> 00` | （设置后主动回查确认） |
| `0x0107` / `0x0207` | 查询/设置 | EQ | `4E 03 00 00 07 01` / `4E 04 00 00 07 02 <eq>` | `4E 04 00 00 07 01 <eq>` |
| `0x0108` / `0x0208` | 查询/设置 | 游戏模式 | `4E 03 00 00 08 01` / `4E 04 00 00 08 02 <0/1>` | `4E 04 00 00 08 01 <0/1>` |
| `0x0106` / `0x0206` | 查询/设置 | 低延迟 | `4E 03 00 00 06 01` / `4E 04 00 00 06 02 <0/1>` | `4E 04 00 00 06 01 <0/1>` |
| `0x0105` / `0x0205` | 查询/设置 | 双设备连接 | `4E 03 00 00 05 01` / `4E 04 00 00 05 02 <0/1>` | `4E 04 00 00 05 01 <0/1>` |
| `0x0109` / `0x0209` | 查询/设置 | 入耳检测 | `4E 03 00 00 09 01` / `4E 04 00 00 09 02 <0/1>` | `4E 04 00 00 09 01 <0/1>` |
| `0x01E1` / `0x02E1` | 查询/设置 | 抗风噪 | `4E 03 00 00 E1 01` / `4E 04 00 00 E1 02 <0/1>` | `4E 04 00 00 E1 01 <0/1>` |
| `0x0204` | 设置 | 编码切换（固件 ≥ 4.8） | `4E 04 00 00 04 02 <codec>` | — |
| `0x0004` | 设置 | 旧版 LHDC 开关（固件 < 4.8） | `4E 04 00 00 04 00 <0/1>` | — |
| `0x0103` | 查询 | 全量状态（仅 Android 定义，未使用） | — | — |

> 规律：查询 = `01 <功能号>`，设置 = `02 <功能号>`（0x0101/0x0201 家族）。设置响应由「设置后延时 100ms 回发查询」获得，非直接应答。

### 2.3 枚举值

**ANC 模式**（Android `AncMode` / Rust `models.rs` 一致）：

| 值 | 模式 | 值 | 模式 |
| --- | --- | --- | --- |
| `0x00` | 关闭 | `0x10` | 试验性降噪 |
| `0x01` | 通透 | `0x11` | 风噪抑制 |
| `0x02` | 普通降噪 | 其他 | 未知（保留原值） |
| `0x03` | 深度降噪 | | |

**EQ 模式**：`0x00` 悔恨之泪 / `0x01` 均衡中正 / `0x02` 欧美澎湃 / `0x03` 真律还原 / `0x04` 游戏优化 / `0x05` 细腻佳音（固件≥4.8）/ `0x06` 温婉人声（固件≥4.8）

**编码**：`0x00` AAC / `0x01` LHDC / `0x02` SBC（SBC 需固件 ≥ 4.8）

**布尔开关**：`0x01` = 开 / `0x00` = 关

**固件版本**：payload = `[sub, main]`（小端序约定），`sub ≥ 8` 解锁扩展 EQ + SBC + 现代编码切换

### 2.4 通信流程（可整体照搬）

**启动查询序列**（连接成功后，每条间隔 100ms）：
`查固件 → 查电量 → 查降噪 → 查EQ → 查游戏 → 查低延迟`（Rust `paced_startup_queries()`）
Android 版完整刷新为 8 条：电量 → 100ms 降噪 → 200ms EQ → 300ms 游戏 → 400ms 低延迟 → 500ms 双连 → 600ms 入耳 → 700ms 抗风噪。

**设置流程**（写后回查确认）：
1. 发送 `02 xx` 设置帧；
2. 等 100ms（命令间隔）；
3. 发送对应 `01 xx` 查询帧，以响应为准更新 UI。

**连接方式**：
- RFCOMM：WinRT `RfcommServiceId::FromUuid(0000a100…)` → `GetRfcommServicesForIdWithCacheModeAsync(Uncached)` → `RequestAccessAsync`（须 Allowed）→ `StreamSocket.ConnectWithProtectionLevelAsync`；
- 串口 SPP 兜底：`serialport` 115200 波特（`connection.rs`）；
- Android：`createRfcommSocketToServiceRecord(SPP_UUID)`，失败回退 `createInsecureRfcommSocketToServiceRecord`。

## 3. 与原道「原点」实测数据对照（关键分析）

### 3.1 逐帧对照

原道 `df21fe2c` 服务连接即推 3 帧（`yuandao-origin.md` §3.12，2026-08-14）：

| 原道帧（hex） | 原道推断含义 | NiceHCK 协议对应 |
| --- | --- | --- |
| `03 01 00 03 \| 44 18 D8` | id=01，3 字节，未知 | 3 字节 payload 对应 NiceHCK 电量帧结构，但 `44 18 D8` ≠ 电量值；**无直接对应**（疑似设备标识/能力集） |
| `03 02 00 06 \| 6C A9 CC 75 1E A4` | id=02，6 字节，设备标识 | **无对应**（NiceHCK 协议无 6 字节 payload 帧） |
| `03 03 00 03 \| 64 64 64` | id=03，3 字节，**疑似 L/R/盒电量** | ✅ **payload 与 NiceHCK 电量响应完全一致**：`64 64 64` = 100/100/100 |

### 3.2 核心结论

1. **payload 语义同族确认**：原道 id=03 帧的 `64 64 64`（= 100/100/100，L/R/盒）与 NiceHCK 电量响应 `4E 06 00 00 05 00 | 64 64 64` 的 **payload 逐字节一致** → 原道的「id=03」就是**电量帧**，字段布局同为 `[左耳, 右耳, 充电盒]`，**盒电量为 0 表示未知**（Android `parsePacket` 逻辑）。

2. **帧格式不同（重要）**：

   | | NiceHCK | 原道（实测推断） |
   | --- | --- | --- |
   | 帧头 | `4E \| len(2 LE) \| 00 \| op(2 LE)`（6 字节） | `03 \| id(1) \| 00 \| len(1)`（4 字节） |
   | Magic | `0x4E` | `0x03` |
   | 长度字段 | 2 字节小端（含保留+Op） | 1 字节（仅 payload 长） |
   | 功能码 | 2 字节小端（0x0101/0x0201 家族） | 1 字节 id（01/02/03…） |

   原道三帧均满足 `03 <id> 00 <len> <payload>` 且 len 与实际 payload 长度精确一致，该格式推断可靠；**NiceHCK 6 字节头格式对原道三帧套用不成立**（长度字段不匹配）。
   → 结论：**原道与 NiceHCK 是 BES 协议族的不同变体**（可能不同 BES SDK 版本：旧版 8 位字段/新版 16 位字段；或品牌定制精简版）。语义（电量 payload、保留位 0x00）同族，帧头不同。

3. **控制服务 UUID 需重新评估**：`0000a100-1000-8000-4e48-434b4354524c` 是 NiceHCK 两版项目**唯一**使用的 RFCOMM 控制服务（作者实测确认），且**原道 SDP 中恰好存在该服务**（之前误判为 QC 数据路径）。原道 SDP 里它与 GATT 的 `0000a100` 服务同 UUID（GATT 端是 LHDC 数据通路），但 **RFCOMM/SPP 端用途需实测**。候选排序应调整为：**`0000a100` ≥ `df21fe2c`**（后者开流成功并推基线帧，但 Android 官方 APP 路径用的是前者）。

4. **行为差异**：NiceHCK 耳机连接后**不主动推帧**（APP 主动查询）；原道连接即推 3 帧基线。可能是原道固件行为差异（推送能力/连接握手），不代表协议不同族。

### 3.3 待验证假设（按优先级）

- **H1（最高）**：原道 `0000a100` 服务是控制通道，且走 NiceHCK 帧格式 → 开流后发 `4E 03 00 00 05 00`（查电量）应收到 `4E 06 00 00 05 00 <L> <R> <Case>`；
- **H2**：原道 `0000a100` 服务可开流但走原道格式 → 推帧应为 `03 xx 00 xx` 格式（与 df21fe2c 一致或类似）；
- **H3**：df21fe2c 是控制通道，命令帧格式为 `03 <id> 00 00`（id 即功能码）→ 发 `03 03 00 00`（推测查电量）应回推电量帧；
- **H4**：两服务分工（df21fe2c 推状态 / 0000a100 收命令），需分别开流对照。

### 3.4 自动校验实测确认（2026-08-14 11:10，`probe\verify-20260814-111107.txt`）—— H1 成立

「协议自动校验」窗口（ProtocolVerifyService）对 YUANDAO OriG in（18:5C:A1:52:50:BF）全自动实测：

1. **`0000a100` 控制通道确认 + NiceHCK 格式确认**：
   - 连接即推：`4E 06 00 00 05 00 64 64 64` = 电量：左 100% 右 100% 盒 100%（NiceHCK 电量帧格式，op=0x0005）；
   - 发 `4E 03 00 00 03 00`（查固件）回 `4E 05 00 00 03 00 08 04` = **固件 4.8**（payload=[sub,main]=[8,4]）→ **查询命令被响应，协议可照搬**。
2. **电量字节 bit7 = 充电中标志**：df21fe2c 推帧 `03 03 00 03 E4 E4 64`——`E4 & 0x7F = 0x64 = 100`，`0x80 | 0x64 = 0xE4`，左右耳充电中（在盒内），盒 100%。解析电量必须 `& 0x7F`，bit7 单独作充电标志。
3. **df21fe2c 仍是原道变体格式**：推 3 帧 `03 01 00 03 44 18 D8` / `03 02 00 06 5F 47 9E 8D 88 31`（设备标识，**每次连接变化**）/ `03 03 00 03 E4 E4 64`；对 NiceHCK 命令无响应 → 与 0000a100 的关系待定（同一耳机两个服务两套格式，0000a100 为主控制通道）。
4. **66666666 / 99999999**：可开流但无推帧无响应 → 非控制通道。
5. **⚠️ 坑 14 顺带定位**：全部服务第二条命令 `Cannot access a disposed object` —— `DataWriter` 每次新建 Dispose 会关底层流（已修，会话级复用）。修复后重测才能拿到完整查询组响应。

### 3.5 全链路验证完成（2026-08-14 11:19:50，`probe\verify-20260814-111950.txt`，耳机在盒内）—— 协议完全确认

坑 14 修复后重跑，**0000a100 查询组 6 条命令全部收到响应**：

| 命令帧 | 响应帧 | 解析 |
| --- | --- | --- |
| `4E 03 00 00 03 00` 查固件 | `4E 05 00 00 03 00 08 04` | 固件 **4.8** |

**结论**：

1. **ANC 模式值映射与原道实测一致**：查询返回 `0x03` = 深度降噪，与 NiceHCK 表（`00关/01通透/02普通/03深度/10试验/11风噪`）完全吻合，**无品牌定制，可直接照搬**。
2. **0000a100 只认 NiceHCK 格式**：原道变体命令（`03 xx 00 00`）对该服务无响应。
3. **df21fe2c 非稳定通道**：本次推帧采集无推帧（11:10 有推）→ 该服务仅在特定状态/时序下推帧，不响应任何命令；0000a100 为唯一控制通道。

5. **固件 4.8**（sub=8 ≥ 4.8）：支持扩展 EQ（细腻佳音/温婉人声）与 SBC 编码切换（开源项目固件能力判定一致）。
