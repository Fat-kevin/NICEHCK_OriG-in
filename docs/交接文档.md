## 1. 项目目标

在 Windows 上连接原道「原点」降噪耳机，提供：设备名、**左右耳/充电盒独立电量及充电状态**、六态 ANC、EQ、游戏/低延迟、双设备、入耳检测、抗风噪和实验性 codec 指令。

**核心约束**：正式控制通道是厂商私有的**经典蓝牙 RFCOMM/SPP**，不是 BLE GATT。已确认服务 UUID 为 `0000a100-1000-8000-4e48-434b4354524c`，帧协议为 NiceHCK/BES `0x4E` 可变长流。品牌协议仍隔离在 `IDeviceProtocol` / `YuandaoProtocol`；GATT 仅保留诊断、探测和标准电量兜底能力。

## 6. 代码规范摘要

- **命名**：类/方法/属性 `PascalCase`，接口前缀 `I`，私有字段 `_camelCase`，异步方法后缀 `Async`，常量 `PascalCase`。
- **异步**：全链路 `await`；**禁止 `.Result` / `.Wait()`**；库代码 `ConfigureAwait(false)`；可取消操作一律传 `CancellationToken`；GATT 读写设超时。
- **异常**：跨层只抛领域异常（`DomainException` 体系）；禁止空 catch 吞异常；日志须含上下文（设备/UUID/操作/帧 hex）。
- **分层**：`using Windows.*` 只出现在 Infrastructure；Application 不引用 WPF；跨层传领域模型/DTO，不传 WinRT 类型。
- **测试**：协议解析逻辑 100% 覆盖（用真机抓包帧作测试数据）；Domain ≥ 80%。
- 详细规范见 `docs/开发文档.md` 第 5 章。

## 7. 协议逆向后的接入点（M0 → M2/M3）

> ⚠️ **v0.2 SPP 方向修正（2026-08-14）**：下方接入点是按「GATT 特征读写」设计的。控制已确认走 **SPP 字节流**（`ISppDeviceSession`），逆向后 `IDeviceProtocol` 契约需相应扩展：`ServiceUuid` 指 **RFCOMM 服务 UUID**（`df21fe2c-2515-…`）；命令经 `ISppDeviceSession.WriteAsync` 发送（非 GATT 特征写）；状态帧从 `DataReceived` 流按帧 id 解析（`03 <id> 00 <len> <payload>`，id=03 疑似电量）。`BatteryCharacteristicUuid` / `AncControlCharacteristicUuid` 两项作废。分层红线不变：WinRT 仍只在 Infrastructure，跨层仍传领域模型（`SppDataReceived` / `BatteryInfo`）。

**改动集中在 `YuandaoProtocol` 一个类 + 对应 Application 服务挂 SPP 会话**（原 GATT 版设计）：

1. 逆向得出以下信息，填进 `YuandaoProtocol`：
   - `ServiceUuid`：私有控制服务 UUID（SPP 下为 RFCOMM 服务 UUID）
   - `BatteryCharacteristicUuid`：双耳电量通知特征 UUID（SPP 下作废，改为帧 id 判定）
   - `AncControlCharacteristicUuid`：降噪控制写特征 UUID（SPP 下作废）
   - `Matches(device)`：按服务 UUID / 名称特征匹配设备
   - `TryParseBattery(frame)`：解析出 `BatteryInfo.FromLeftRight(left, right, casePct)`
   - `BuildAncCommand(mode)`：命令字节帧
   - `TryParseAncState(frame)` / `IsAncStateNotification(uuid)`：降噪状态
2. `BatteryMonitorService` 检测到 `BatteryCharacteristicUuid` 非 null 即自动启用双耳电量；`NoiseCancellingService` 检测到 `AncControlCharacteristicUuid` 非 null 即自动启用降噪切换（含写后回读确认）。
3. 用真机抓到的帧补测试用例（解析逻辑覆盖）。

> 逆向工具链与步骤见 `docs/开发文档.md` 第 7 章（Android HCI snoop + Wireshark + JADX + nRF Connect）。

## 8. 已知坑与决策记录（重要）

| # | 坑 | 说明 / 规避 |
| --- | --- | --- |
| 1 | **WPF 引用 WinRT 报 CS0234「Windows 不存在」** | TFM 必须带 Windows 版本：`net8.0-windows10.0.19041.0`（自动注入 Windows SDK 投影）。纯 `net8.0-windows` 不够。 |
| 2 | **`Application` 被解析为命名空间** | 本项目命名空间 `YuandaoTws.App` 内写 `Application` 会匹配到 `YuandaoTws.Application`（Application 层命名空间）而非 `System.Windows.Application`。**必须全限定** `System.Windows.Application`（见 `App.xaml.cs`、`MainViewModel.cs`）。 |
| 3 | **`GattSession` 命名空间** | 位于 `Windows.Devices.Bluetooth.GenericAttributeProfile`，不在 `Windows.Devices.Bluetooth`（见 `GattConnectionFactory.cs`）。 |
| 4 | **WinRT 异步取消** | 用 `IAsyncOperation.AsTask(cancellationToken)`（CsWinRT 提供，`System` 命名空间）。 |
| 5 | **部分耳机电量只 Notify 不 Read** | 主动 `ReadAsync` 返回 null 属正常；必须订阅 Notify。`BatteryMonitorService` 已实现「订阅 + 尝试读一次」双保险。 |
| 6 | **非打包应用蓝牙 capability** | 多数 GATT 客户端操作可直接工作；个别受限时兜底改 MSIX 打包。未配对设备访问受限 → 引导用户先配对。 |
| 7 | **特征枚举重名** | Domain 的 `GattCharacteristicProperties` 与 WinRT 同名，Infrastructure 内用 `using GattProps = ...` / `WinRtGattProps = ...` 别名区分。 |
| 8 | **DI 生命周期** | 服务全部注册为 Singleton（应用单窗口单会话场景足够）；会话本身是运行时创建的 `IGattDeviceSession`，通过 `HeadsetConnectionService.SessionChanged` 事件下发给电量/降噪服务。 |
| 9 | **协议逆向改走「Windows 自探测」路径** | 联网检索确认网上无原道 Origin 私有协议公开资料；且 Windows 端 WinRT 可枚举耳机全部 GATT 服务/特征（`GattDeviceSession.EnumerateServicesAsync`，Uncached 防陈旧），**不再强制 Android 抓包**。应用内「协议探测」窗口（FR-10）已完成：枚举 / 读值 / 监听通知 / 导出报告。仍需真机操作（切降噪、看电量）配合定位特征（2026-08-13）。 |
| 10 | **已连接耳机的 BLE 身份扫不到** | TWS 耳机通常经**经典蓝牙**作音频连接（Windows 设置里配对 A2DP），其 **BLE 控制通道不会出现在 BLE 广播列表**，系统 BLE 记录里也没有它，故仅靠 `DeviceWatcher` 扫不到。解决（`BluetoothDeviceScanner`）：扫描时额外枚举「**已配对经典蓝牙设备**」（`BluetoothDevice.GetDeviceSelectorFromPairingState(true)`），按**相同 MAC** 用 `BluetoothLEDevice.FromBluetoothAddressAsync` 探测其 BLE 控制通道。⚠️ 遍历时 **BTHENUM 功能端点（AVRCP 传输、设备标识服务等）不是有效 `BluetoothDevice`，`FromIdAsync` 会抛 `ArgumentException`**，必须逐个设备单独 `try/catch` 跳过，否则整个探测中断（2026-08-13）。 |
